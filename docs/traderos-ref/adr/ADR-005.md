# ADR-005: SQLite Dev / PostgreSQL Production Database Strategy

## Status
Accepted

## Context
TraderOS currently uses SQLite via the `sqlite3` Python module. As the system grows,
production deployments require a more robust database (PostgreSQL) for concurrent
access, reliability, and performance. However, SQLite remains ideal for local
development, testing, and single-user scenarios.

## Decision
Adopt a dual-database strategy:

- **Development & Testing**: SQLite (file-based, zero configuration)
- **Production**: PostgreSQL (connection pool, concurrent access)

The migration between databases is handled through:
1. A migration framework (`database/migration_manager.py`) that manages schema
   versioning with Python-based migrations
2. Repository pattern extraction (planned for future work packages) to abstract
   persistence behind interfaces

## Consequences

### Positive
- Developers can run the full system locally without PostgreSQL
- Tests are fast and isolated with in-memory/temporary SQLite databases
- Schema changes are versioned, reversible, and automated
- Production path to PostgreSQL is clearly defined

### Negative
- Some SQL dialect differences (e.g., `INSERT OR REPLACE` vs `ON CONFLICT`) must
  be handled during migration
- Dual maintenance until the repository pattern is fully extracted

## Migration Path
1. SQLite remains the default for development
2. Schema is defined in versioned migration files under `database/migrations/`
3. When PostgreSQL is needed, a PostgreSQL adapter is added alongside the
   migration framework
4. The existing `DatabaseManager` is gradually replaced with repository
   interfaces (see ADR-00X, planned)

## Compliance
[Constitution: C:8.18] Database migrations are automated and versioned.
